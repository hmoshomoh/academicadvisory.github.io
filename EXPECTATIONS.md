# EXPECTATIONS.md — build gate

Derived from `Academic Support & Complaints System - MVP Build Spec (1).md`.

Rules for this file (from the spec):

- An item is checked (`- [x]`) **only** when a test passes or the feature was personally walked through. Never because the code merely runs without erroring.
- Phase *N+1* is not started until every item in phase *N* is checked.
- A requirement that cannot be met as scoped stays unchecked with a one-line blocker note underneath — never dropped, never reinterpreted.

Verification legend, appended to each checked item:

- `(test: <name>)` — an automated test asserts it.
- `(walkthrough)` — driven through the running app by hand and observed.

---

## Phase 1 — Auth + roles + base schema

- [ ] Django project runs against PostgreSQL (not SQLite).
- [ ] A student can register through a form and gets an account.
- [ ] A registered user can log in and log out.
- [ ] Passwords are stored hashed, never in plaintext.
- [ ] CSRF protection is active on every POST form.
- [ ] The three Django Groups `Student`, `Adviser`, `Admin` exist and are created by a repeatable command (not hand-clicked in admin).
- [ ] Registration puts the new user in the `Student` group.
- [ ] `Student` model exists, one-to-one with `User`, with an FK to an assigned `Adviser`.
- [ ] `Adviser` model exists, one-to-one with `User`.
- [ ] `Admin` role is represented and reachable (group membership + staff access).
- [ ] `AcademicRecord`, `Recommendation`, `ComplaintCategory`, `Complaint`, `ComplaintStatusLog`, `Notification` tables are all created by migrations.
- [ ] Every view that shows user data requires login; anonymous access redirects to the login page.
- [ ] A student cannot reach adviser-only or admin-only views (403 / redirect).
- [ ] An adviser cannot reach admin-only views.
- [ ] Each role lands on its own dashboard after login.
- [ ] Templates use Bootstrap 5 and render on a mobile viewport width without horizontal scroll.

## Phase 2 — Academic records + GPA/CGPA + recommendations

- [ ] An `AcademicRecord` stores a semester's courses with credit units and grades for one student.
- [ ] GPA is computed per semester as credit-weighted grade points.
- [ ] CGPA is computed across all of a student's semesters, credit-weighted.
- [ ] GPA/CGPA of a student with no records is handled without crashing (no division by zero).
- [ ] Grade letters map to grade points through one documented scale.
- [ ] A student can view their own GPA per semester and their CGPA.
- [ ] Recommendations are generated by rules from performance thresholds, not written by hand.
- [ ] A `course advice` recommendation is generated for satisfactory performance.
- [ ] A `warning` recommendation is generated when performance falls below the warning threshold.
- [ ] A `probation alert` recommendation is generated when performance falls below the probation threshold.
- [ ] Recommendations are attached to the `AcademicRecord` they were derived from.
- [ ] Regenerating recommendations for the same record does not create duplicates.
- [ ] A student sees their own recommendations and no one else's.
- [ ] An adviser sees the academic records of students assigned to them.
- [ ] An adviser cannot see the academic records of a student not assigned to them (enforced by a queryset filter, not template hiding).
- [ ] A student can send an advisory request to their adviser.
- [ ] An adviser can respond to an advisory request, and the student sees the response.

## Phase 3 — Complaint submission + anonymous path + tracking reference

- [ ] A logged-in student can submit a named complaint tied to their account.
- [ ] A complaint can be submitted anonymously via a toggle on the same form.
- [ ] A complaint carries a category chosen from `ComplaintCategory`.
- [ ] A complaint accepts a file/image attachment, and the file is stored and retrievable.
- [ ] Submission returns a unique tracking reference to the submitter.
- [ ] Tracking references are unique across complaints.
- [ ] The tracking reference is unguessable (not sequential, not derived from the student id).
- [ ] Anyone holding a reference can check that complaint's status without logging in.
- [ ] The status-check page reveals status and history only — never the submitter's identity.
- [ ] For an anonymous complaint, no student identity is stored on the record at all (verified at the database level, not just excluded from views).
- [ ] An anonymous complaint's stored data cannot be joined back to a `Student` row through any FK, column, or table.
- [ ] An admin viewing an anonymous complaint sees no identity, and the UI states the complaint is anonymous.
- [ ] An adviser cannot reach complaints at all, anonymous or named.
- [ ] `ComplaintStatusLog` rows for an anonymous complaint contain no submitter identity.
- [ ] A named complaint shows the submitter's identity to admins (the contrast case that proves the anonymous path is doing work).
- [ ] A student can list their own named complaints; anonymous ones do not appear in any student's list (they are unlinkable by design).
- [ ] Uploading a non-attachment-sized/typed junk file is rejected with a form error rather than a 500.

## Phase 4 — Admin review: categorize / resolve / escalate + status log

- [ ] An admin can list all complaints.
- [ ] An admin can change a complaint's category.
- [ ] An admin can resolve a complaint with a resolution note.
- [ ] An admin can escalate a complaint.
- [ ] Every one of those actions writes a `ComplaintStatusLog` row with who, what, when.
- [ ] `ComplaintStatusLog` is append-only: existing rows cannot be edited or deleted through the app.
- [ ] The log for a complaint is shown in chronological order on its detail page.
- [ ] A complaint's current status always matches its latest log row.
- [ ] A student/adviser cannot perform any of these admin actions (403).
- [ ] Status transitions are constrained to the defined set of statuses.

## Phase 5 — Notifications

- [ ] A `Notification` is created on every complaint status change.
- [ ] A named complaint's submitter receives the notification.
- [ ] An anonymous complaint's status change creates a notification that is not addressed to any student (no identity leak).
- [ ] A user sees their own notifications and no one else's.
- [ ] A notification can be marked read, and unread count reflects it.
- [ ] An unread-notification indicator is visible in the app chrome.

## Phase 6 — Admin analytics dashboard + export

- [ ] The dashboard shows total complaint volume.
- [ ] The dashboard shows a breakdown by category.
- [ ] The dashboard shows a breakdown by status.
- [ ] The dashboard shows average resolution time for resolved complaints.
- [ ] The dashboard is reachable by admins only.
- [ ] A report can be exported (CSV download).
- [ ] The export contains no submitter identity for anonymous complaints (checked against the exported bytes).
- [ ] The dashboard renders with zero complaints in the database without crashing.

## Phase 7 — Testing pass + manual click-through + deployment shape

- [ ] A minimal automated test suite passes (`manage.py test`), kept few and focused per the spec.
- [ ] Student role clicked through once per feature area: register, log in, view GPA/CGPA + recommendations, advisory request, submit named complaint, submit anonymous complaint, track by reference, notifications.
- [ ] Adviser role clicked through: log in, see assigned students' records, respond to an advisory request, blocked from admin views and complaints.
- [ ] Admin role clicked through: log in, list complaints, categorize, resolve, escalate, see status log, dashboard, CSV export.
- [ ] A seed/demo data command exists so the walkthroughs are reproducible.
- [ ] `requirements.txt` pins the dependencies.
- [ ] `Procfile` runs Gunicorn; the app reads `DATABASE_URL`, `SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS` from the environment so a managed PaaS can run it.
- [ ] Static files are served in production mode (WhiteNoise) and `collectstatic` succeeds.
- [ ] `README.md` documents local setup, the grade scale, the recommendation thresholds, and the anonymity design decision.
- [ ] No REST API layer, no SPA, no DRF in the dependency list (scope discipline).
- [ ] Nothing outside the spec was added.
