# Academic Support & Complaints Management System

A college-project MVP: a Django app with an academic-advisory module (GPA/CGPA plus
automatic recommendations) and an anonymity-preserving complaints module.

Built to the spec in `Academic Support & Complaints System - MVP Build Spec (1).md`.
Every requirement is tracked as a checkable line in [`EXPECTATIONS.md`](EXPECTATIONS.md).

## Stack

Python 3 + Django 4.2 (server-rendered, no REST API and no SPA), PostgreSQL, Django
templates with Bootstrap 5, Django's built-in auth with `Student` / `Adviser` / `Admin`
groups, Gunicorn behind a managed PaaS.

## Local setup

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
createdb acad_app
python manage.py migrate
python manage.py bootstrap_roles     # the three groups + default complaint categories
python manage.py seed_demo           # demo advisers, students, results and complaints
python manage.py runserver
```

`DATABASE_URL` defaults to `postgres://$USER@localhost:5432/acad_app`. Set it to point
somewhere else.

## Grade scale

A 5.0-point scale, defined once in `academics/grading.py`. No other module defines a
second scale.

| Grade | A | B | C | D | E | F |
| --- | --- | --- | --- | --- | --- | --- |
| Points | 5 | 4 | 3 | 2 | 1 | 0 |

GPA is the credit-weighted average of one semester's courses:
`Σ(units × points) / Σ(units)`. CGPA is the same formula over every semester's courses,
so it is weighted by credit units rather than being an average of GPAs. With no courses
recorded, both return `None` and render as `—` — there is no division by zero.

## Recommendation thresholds

Recommendations are generated by rules in `academics/recommendations.py`, never written
per student, and regenerating them for a record updates the existing rows instead of
adding duplicates. Thresholds, on the 5.0 scale:

| GPA | Recommendation |
| --- | --- |
| `< 1.50` | **Probation alert** — at risk of academic probation, see an adviser, reduce load |
| `1.50 – 2.49` | **Warning** — prioritise weak courses, check in with the adviser |
| `≥ 2.50` | **Course advice** — keep the current pattern, consider building electives |

Any failed course in the record is named in whichever recommendation fires, as a retake
list.

## The anonymity design decision

The spec's hard constraint is that anonymity survives the whole lifecycle, and it warns
against just nulling out a student FK.

**The decision: an anonymous complaint stores no submitter identity at all.** Not a
nulled FK to a row kept elsewhere, not a hash of the student, not an audit column, not a
side table mapping references to students. `complaints_complaint.student_id` is `NULL`,
and nothing else on the row or in any related table points at a `Student`.

What that buys, and how each part is enforced:

- **No query, join or export can re-link it**, because there is no column to join on.
  `Complaint.objects.for_student()` filters `is_anonymous=False` and matches nothing
  anonymous by construction. The CSV export writes `submitter_label`, which returns
  `"Anonymous"` because it has nothing else to return.
- **The leak is unrepresentable, not merely avoided.** A database `CHECK` constraint,
  `anonymous_has_no_student`, rejects any anonymous row carrying a student — so a raw
  `UPDATE`, a data migration or a shell session cannot create one either. `Complaint.save`
  raises the same refusal earlier, with a readable error.
- **The audit trail stays clean.** The opening `ComplaintStatusLog` row for an anonymous
  complaint records no actor and the frozen label `"Anonymous submitter"`. Later rows
  name the *admin* who acted, which is the point of the trail and reveals nothing about
  the submitter.
- **Notifications have nowhere to leak to.** A status change on an anonymous complaint
  creates a `Notification` with `recipient = NULL`; it is read through the tracking page
  instead of an inbox.

The cost, accepted deliberately: the tracking reference is the **only** link back, and it
lives with the submitter, outside this database. A student who loses it cannot recover it,
and no administrator can look it up for them. That is what makes the anonymity real.
The reference is a `secrets`-generated 10-character token over a 32-character alphabet
(`ACS-XXXXXXXXXX`), so it is neither sequential nor derived from the student, and holding
one reference tells you nothing about any other.

## Audit trail

`ComplaintStatusLog` is append-only, and that is enforced in code rather than by
convention: `save()` refuses to write a row that already has a primary key, `delete()`
always raises, and the Django admin registration denies add, change and delete. Every
admin action on a complaint — re-categorise, move to review, escalate, resolve — goes
through `complaints/services.py`, which is the only write path, so the log row and the
notification cannot be forgotten at a call site.

## Tests

```bash
python manage.py test
```

The suite is deliberately small, per the spec, and covers what reading the code cannot
prove: the GPA/CGPA arithmetic, each recommendation threshold, adviser scoping, the
anonymity guarantee at both the model and database level, tracking without login, the
append-only log, role permissions, and the export's contents.

## Deployment

Any managed PaaS with a Postgres add-on (Render, Railway, Fly.io). The `Procfile` runs
migrations and `bootstrap_roles` on release, then Gunicorn; WhiteNoise serves static
files. Set these environment variables:

| Variable | Notes |
| --- | --- |
| `SECRET_KEY` | Required. Long and random. |
| `DEBUG` | `False` in production. |
| `ALLOWED_HOSTS` | Comma-separated hostnames. |
| `DATABASE_URL` | Provided by the Postgres add-on. |
| `CSRF_TRUSTED_ORIGINS` | Comma-separated, e.g. `https://your-app.onrender.com`. |

TLS is the platform's; Django only insists on it via `SECURE_SSL_REDIRECT`.

Known limitation: complaint attachments are stored on the local filesystem, which is
ephemeral on most PaaS dynos. Attach a persistent disk if uploads must survive a
redeploy.
